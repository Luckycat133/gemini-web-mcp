# Gemini Web MCP Development

Work in a checkout of `gemini-web-mcp`. Read its `AGENTS.md`, inspect the current
changes and affected implementation/tests, and preserve unrelated work. Package
metadata, tool schemas and dated acceptance evidence come from the checkout.

## Choose the shared owner

The primary, compact and focused servers are adapters over shared services.
Keep existing tool names and argument compatibility. Choose the lowest shared
owner for a change; [architecture.md](references/architecture.md) maps source
boundaries, products, state and RPC contracts.

Important cross-surface contracts:

- Structured states agree with compatibility text. Mutations require positive
  read-back; artifact completion requires usable output of the requested kind.
- Long operations preserve explicit handles and observed source IDs. Recovery
  does not resubmit generation after a timeout or reconnect.
- Local operation/cleanup persistence stores metadata and artifact locators,
  excluding credentials, prompts, chat/report text and generated bytes.
- Reverse-engineered requests and parsers stay at the infrastructure boundary;
  changed upstream contracts need current evidence and shape fixtures.

## Select the relevant reference

- [tool-design.md](references/tool-design.md): when changing tools, Skill
  discovery, result contracts or agent handoffs.
- [validation.md](references/validation.md): choose checks for the changed
  boundary; distinguish offline, protocol, package, agent-use and live evidence.
- [roadmap.md](references/roadmap.md): when planning a new capability or the next
  development package; consult current repository status first.

Fixes, documentation, packaging and feature work have different verification
needs. Report actual checks and remaining limitations. Update Skills when
supported tasks or reusable operating guidance change; keep run-specific
observations in repository evidence documents.
