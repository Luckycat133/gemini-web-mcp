# Operation recovery and automatic cleanup

Updated: 2026-10-03.

`gemini-mcp-create` starts video/music asynchronously. `gemini-mcp-assist`
uses the same service for Deep Research. Preserve the returned opaque
`operation_id`; status, result and cancel always address that exact operation.
The assist server keeps five tools: `gemini_research` takes an explicit
`action` for start/status/result/cancel. The create server has seven tools,
including separate operation status/result/cancel tools.

## Start once

Supply a random `idempotency_key` when starting asynchronous work. Reusing
that key with the same operation kind retrieves the existing handle if the
start response was lost. Do not derive the key from a prompt, account name
or private content. Reusing it does not change the original request.

Poll the existing handle after a timeout, interruption or reconnect. Recovery
reads an observed provider/chat ID or returns saved Artifact locators; it never
resubmits the prompt. If the interrupted request has no observed source ID,
the service cannot recover it or prove that no request was created. Inspect
Gemini Web before deciding to start a different request.

`accepted`, `running`, `queued`, `partial`, `timed_out`, `failed`,
`cancel_requested`, `cancelled` and `expired` stay distinct. Video completion
requires verified local video; music requires audio and any returned companion
outputs to be saved and verified. Research requires a saved report. A provider
completion message or local preview alone is insufficient.

Cancellation is best effort. `cancel_requested` does not prove that Google
stopped generation. `cancelled` requires observed provider confirmation or a
transactional `local_cancelled_before_start` result proving the producer never
started. In the latter case `provider_confirmed` remains false.
Cancellation never authorizes deleting the source or restarting generation.

## Local state

One SQLite database owns `operations` and `cleanup_jobs`. Set
`GEMINI_STATE_DB_PATH` to an absolute private path when several client
processes must share recovery state. Defaults:

| Platform | Default database |
| --- | --- |
| macOS | `~/Library/Application Support/gemini-web-mcp/state.sqlite3` |
| Linux | `~/.local/state/gemini-web-mcp/state.sqlite3` |

Concurrent initialization retries SQLite busy errors under one three-second
budget before the transaction body starts. Other database errors fail directly;
migrations, caller statements and commits are not replayed by this retry.

The database and its `.key` identity file use restricted permissions. Keep
both files together across restarts. The store contains IDs, timestamps,
attempts, state, stable error codes, verification, Artifact locators, output
destination and retention policy. It contains no Cookies, prompts, chat/report
text, raw responses or generated bytes. Media/report files remain separate.

The authenticated local runtime requires POSIX file ownership, restrictive
permissions and no-follow protection. Windows lacks the currently required
APIs and is explicitly unsupported; no Windows ACL acceptance is claimed.

Operation metadata expires seven days after allocation. Expired handles return
`OPERATION_EXPIRED`; removing metadata does not delete a file or an account
resource. Cleanup jobs retain retry authority until completion, explicit
retention/cancellation, or an authentication replacement that withdraws the
current process's old jobs; completed/withdrawn metadata can be pruned after its
retention window.

Transactional version checks and renewable leases allow one process to execute
generation/recovery/cleanup for a record. Other clients observe the saved state.
After a hard crash, a lease may remain active for up to 270 seconds before
operation recovery can claim it. Cleanup uses a separate 60-second renewable
lease. A late failure cannot replace already verified
completion. Graceful process shutdown preserves observed source IDs.

## Credential isolation

The effective `__Secure-1PSID` credential is keyed with a local HMAC identity
secret. Only matching credential material and the original key access the same
state. Refreshing `__Secure-1PSIDTS` preserves this scope. A different or missing
PSID cannot execute another scope's cleanup or inspect its operation handles.

This is a credential lineage boundary, not a verified Google account ID.
PSID rotation may isolate older jobs even for the same human account. Browser
multi-account selection is not inferred from the foreground Gemini page. Do
not merge scopes or scan unrelated history to recover an inaccessible job.

## Cleanup policy

Only a newly created source chat observed in the request qualifies for
automatic cleanup. All requested outputs must be saved and verified, or the
response must be definitively empty. Queued, remote-only, partial, unverified,
interrupted and failed read-back results retain their source for recovery.

`retain_chat=true` withdraws unclaimed cleanup. A positive
`delete_after_seconds` persists a delayed job. The worker resumes due jobs
after a running server binds an authenticated client under the same credential
scope. Starting an idle stdio process alone does not authenticate or delete. With every server stopped,
no remote deletion runs.

Each attempt rechecks authority before claiming deletion and requires fresh
positive absence read-back. Pending, failed or accepted deletion is not success.
Retaining/cancelling a claimed job cannot retract an in-flight remote RPC; if
that attempt fails, withdrawn work is not retried. Artifact readiness and
cleanup verification are reported independently.

The account facade `gemini_cleanup` provides scoped, paginated local job
status, bounded due-job execution, exact-job retry and cancellation. It does
not scan remote history for these actions. Broad marker-based test cleanup is
a separate explicit action with `dry_run=true` by default.

For disposable tests, record every returned source ID, finish file verification
and confirm cleanup. Explicitly discarded test results may be deleted by their
known ID even when generation failed. Unknown ownership is retained.
Use the host's connected MCP tools for manual deletion, or a real stdio MCP
client when testing an installation or unconnected surface. A browser deletion
or direct agent-side SDK/RPC call is separate diagnostic evidence.
