## Current Runtime

The repository exposes a 17-tool function surface and a 17-tool account surface, plus the explicit-profile primary, four-tool compact and five-tool assist compatibility surfaces and existing Runtime Skills. Shared services cover chat/session lifecycle, Notebook source context, Gemini Task, Artifacts, source-evidence classification, mixed-input understanding, Deep Research starts and explicit recovery, typed history, account workflows, packaging, and protocol compatibility.

The compatibility Runtime Skill is now task-first: it routes second opinion/search/understanding/Research, creation, or explicit account work without requiring a manifest call before every known workflow. Generated Artifacts are intended for downstream agent use, not merely path reporting.

## Settled Product Architecture

One repository and Python distribution exposes two business surfaces:

| Surface | Entrypoint | Scope |
| --- | --- | --- |
| Function | `gemini-mcp-function` | Assistance, chat, Task, media, research and operation recovery (17 tools) |
| Account | `gemini-mcp-account` | Explicit history, Notebook/Task metadata, Chat scheduled actions, Gems, inventory and MCP-owned cleanup (17 tools) |

`gemini-mcp-server` without `GEMINI_TOOLS` serves the function surface; explicit profiles keep their existing behavior. Assist and compact remain compatible. Cookie, Doctor and local Prompts tools stay outside the two business surfaces. `gemini_cleanup` targets only chats recorded as MCP-owned, never title matches.

Public tools use `gemini_` prefixes. `gemini_ask` remains distinct. Image, video, music and Deep Research start in the background by default. Function Ask with `notebook_ids` is background ordinary Chat (`execution_mode="chat"`), while `gemini_run_task` explicitly starts Task (`execution_mode="task"`). Both use 600-second phase timeouts by default. Operation metadata uses local SQLite with explicit opaque handles and primary `gemini_get_operation_status` / `gemini_get_operation_result` tools for restart and cross-client reads. Ordinary records have seven-day retention; an expired research record with a protected upstream chat remains recoverable until protection is released. A caller-supplied handle is needed to locate work if the initial response is lost. No prompts, chat/report text, Cookies, raw responses, or generated bytes are persisted in the ledger; verified answer files live separately with only their locators and verification metadata in SQLite.

A separate account-scoped SQLite cleanup queue survives restart and records verified deletion, leases, and retry state. Completed one-shot requests automatically attempt verified deletion before returning by default; failed verification stays pending for retry. Active sessions are preserved for subsequent turns and cleaned up after they end. Unread research is protected until the server assembles its report or a definite pre-start failure is established. Unresolved background media, Research, Task and Notebook Chat are protected while their outcome is unknown. Task and Notebook Chat workers verify the exact completed reply and save and verify its full local answer Artifact before owned-chat cleanup, without waiting for the caller to request the result. Saved results remain readable by the original handle after restart. Notebook objects and sources are not temporary-chat cleanup targets. Cancellation remains unimplemented.

Account `gemini_notebooks` defaults to the Notebook source-picker view (`source="notebooklm"`); `source="gemini"` retains the same integrated product's project view and chat moves with fresh exact-target resolution. `gemini_tasks` lists/gets metadata without answer text and explicitly deletes exact Task chat IDs with independent read-back. Task schedules remain separate from Chat scheduled actions; bounded progress and explicit browser inputs are available, while exclusive handoff, Task pause/resume and automatic permission approval remain unavailable. See [Notebook, Chat and Task workflows](notebook-task-workflows.md).

The explicit-profile, assist and low-token servers remain compatibility surfaces.
